# Deployment (Render)

Nothing in Gates 0-7 built any deployment infrastructure — every prior
report's "run it locally" instructions were as far as this project went.
This document and `render.yaml` at the repo root are new, written to get a
real public URL up on [Render](https://render.com). **This has never been
applied** — that requires a Render account, which only you can create — so
treat this as a strong starting point, not a guaranteed one-click deploy.

## What gets deployed

| Render resource | Purpose |
|---|---|
| `quest-board-postgres` | Managed Postgres — needs the `postgis` extension enabled (see below) |
| `quest-board-redis` | Session store + future job queue (ADR-004) |
| `quest-board-api` | The Express API (`apps/api`), plus migrations/seed on every deploy |
| `quest-board-web` | The Next.js app (`apps/web`) |

## Prerequisites

1. A GitHub repo with this code pushed to it (Render deploys from a
   connected repo). `gh` CLI is already installed locally — run
   `gh auth login` yourself, then let me know and I'll create the repo and
   push.
2. A free Render account (render.com — sign up yourself; I can't create
   accounts on your behalf).

## Steps

1. In Render's dashboard: **New > Blueprint**, select the GitHub repo.
   Render should auto-detect `render.yaml` at the repo root and propose
   the 4 resources above.
2. Before applying, review the two env vars marked `sync: false` in
   `render.yaml` (`GOOGLE_PLACES_SERVER_API_KEY`, `AI_PROVIDER_API_KEY`) —
   **leave them blank**. Every provider adapter in this codebase runs in a
   documented stub/degraded mode without them (ADR-005, ADR-006), which is
   the correct state until the Gate 0 licensing questions
   (`docs/gate-0/04-provider-licensing-questions.md`) are actually
   resolved. Setting a real key here before that review is done would be
   the first time this project incurred real provider cost or licensing
   exposure — don't do it as a side effect of deploying.
3. Apply the blueprint. `SESSION_SECRET` is auto-generated by Render
   (`generateValue: true`); `WEB_ORIGIN`, `API_BASE_URL`, and
   `NEXT_PUBLIC_API_BASE_URL` are wired to each other's deployed hostnames
   automatically.
4. **Verify PostGIS is actually enabled** — this is the one real unknown
   this blueprint can't resolve in advance. Render's managed Postgres
   *should* allow `CREATE EXTENSION postgis` (migration `0001` already
   runs it), but plan-level restrictions vary and I can't confirm this
   without an account. If the API's first deploy fails during
   `preDeployCommand` (`npm run db:migrate`), this is the first thing to
   check — open Render's Postgres shell and try
   `CREATE EXTENSION IF NOT EXISTS postgis;` directly. If it's genuinely
   not permitted on your plan, the fallback is pointing `DATABASE_URL` at
   an external Postgres known to support it (Neon and Supabase both do)
   instead of Render's own Postgres — everything else in this blueprint
   stays the same.

## Known Render free-tier quirks (not bugs in this app)

- **Free web services spin down after ~15 minutes idle** and take a few
  seconds to cold-start on the next request — the first load after a quiet
  period will be slow. Expected, not broken.
- **Free Postgres databases on Render expire after a fixed period** (Render
  states 30 days on their free tier as of this writing — confirm current
  terms in their dashboard) unless upgraded to a paid plan. Don't be
  surprised if the pilot data disappears after that if it's still on the
  free database.
- **Free Redis has a small size cap.** Session data is tiny per user, but
  this is worth knowing if sessions start behaving oddly under real load.

None of these are things to "fix" in the code — they're the cost of a free
tier, and exactly the kind of operational detail Section 49's "geographic
readiness"/pilot-scope questions (still open in
`docs/gate-0/06-decision-log.md`) are meant to force a real decision about
before an actual public pilot, not a real deployment used only to view the
running app.

## Post-deploy verification checklist

Once both services are live:

1. `https://<api-host>/health` → `{"status":"ok", "checks": {...}}` with
   `database`/`redis` both `"ok"` and `placesProvider`/`aiProvider` both
   `"degraded"` (expected — no keys configured).
2. Visit the web app's URL → home page loads, `/discover` shows the 6 seed
   quests.
3. Register an account, confirm the session persists across page loads
   (this is the cross-site cookie fix from Gate 7's continuation — if this
   silently fails, check the browser's dev tools Network tab for a
   rejected `Set-Cookie` header, which would mean `SameSite=None` isn't
   taking effect for some reason).
4. Run through the Forge flow (generate → save draft → submit → publish
   as a trusted creator — see `docs/gate-4/00-forge-report.md`'s manual
   verification steps for how to flip `creator_trust` via Render's
   Postgres shell instead of local `docker exec`).
5. Start and complete a quest, confirm XP/badges appear on `/profile`.

This is, genuinely, the first time any of this would be verified running
for real — see `docs/gate-7/01-mvp-done-checklist.md` for why that matters
more than any individual feature list.
